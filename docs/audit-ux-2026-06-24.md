# UC Meeting-Ops UI/UX + Frontend Quality Audit

Date: 2026-06-24  
Scope: `frontend/src/` only; audit and recommendations, no product code changes.

## Executive summary

Meeting-Ops has unusually broad product coverage for a browser-first recorder: desktop and mobile capture, local-only sessions, server completion, upload recovery, diarized session review, cross-meeting chat, knowledge graph, settings, and admin workflows are all represented. The strongest UX work is in the newer recording path: the desktop recorder persists chunks in IndexedDB, mobile capture uploads chunks incrementally, destructive recording actions use accessible confirmations, and upload processing now has a REST fallback when its WebSocket closes.

The highest-risk remaining issue is not visual polish but trust. Several failure paths still render an empty or indefinitely processing state instead of an explicit failure:

1. A Sessions API failure is converted into an empty session list, so a user can be told “No Sessions Found” when their meetings are merely unreachable.
2. Upload fallback monitoring still has two spinner-forever cases: an open-but-silent socket disables polling, and the polling ceiling stops without assigning a terminal state.
3. A generic processing Session Details page does not poll for completion; only the separate full-audio reprocess metadata path does.
4. Mobile capture reports “Done. Server is processing” even when the request that starts server reprocessing failed.
5. Several core overlays remain hand-rolled and do not trap focus, restore focus, close on Escape, or expose dialog semantics.

The UI is also carrying two competing visual systems. Most of the authenticated shell is fixed dark zinc, while desktop Session Details is fixed light gray/white. The Theme setting only toggles document classes; major screens do not consume them, so “Light” is not a reliable app-wide theme.

### Top user-facing problems

- **Sessions can appear lost during an API outage.** The fetch path logs the failure, replaces server data with an empty array, and renders the first-run empty state.
- **Processing can remain non-terminal.** Upload tracking, Session Details, and TTS each contain live-channel paths with no complete fallback/watchdog.
- **Mobile completion can claim work started when it did not.** `/finalize-audio` failure is explicitly treated as non-fatal, but the next UI state promises server processing.
- **A first-session CTA is broken on mobile.** “Record on this phone” navigates to an undefined `/recording` route.
- **Keyboard and screen-reader behavior is inconsistent.** The shared Radix dialog is sound, but sharing, email, reprocess, upload, settings voiceprint, and admin overlays bypass it.
- **First load is expensive.** The production build emits multi-megabyte entry chunks plus a 21.6 MB WASM asset; this directly competes with the already-large first-run AI model download.

## Verification performed

- Read `frontend/CLAUDE.md`.
- Inspected router, app shell, auth/org/recording/upload contexts, core pages, mobile variants, settings, AI chat, knowledge graph, admin pages, modal primitives, and upload/recording utilities.
- `cd frontend && npm run build`: **passes**.
  - Build output includes entry chunks of approximately **4.18 MB** and **6.03 MB** minified, an approximately **895 KB** transformers chunk, and a **21.6 MB** ONNX Runtime WASM asset.
  - Vite warns that `BrigadeGraphViewer` is both statically and dynamically imported, so the Session Details dynamic import does not isolate it into a separate chunk.
- `cd frontend && npx vitest run`: **fails** with **1 failed, 132 passed**.
  - `frontend/src/__tests__/Landing.test.tsx:31` expects an old H1; the page now ships “The open standard for conversation intelligence.”
  - Radix also reports missing descriptions for two Speaker Library dialogs during tests.
- The Vite development server starts successfully on port 7777. An authenticated flow walkthrough was not possible in this environment because the backend/session was not available, so runtime conclusions below are tied to component and state-machine behavior.

## Findings

### [P0] Sessions / library load — `frontend/src/pages/Sessions.tsx:1231` (Sessions)

**User moment:** A user opens Sessions during a server outage, expired upstream session, or transient network failure.

**What the user experiences:** The failed server request is only logged. `serverSessions` remains empty, the component replaces its session state with local-only results, and the page then renders “No Sessions Found” / “Create your first session” at `frontend/src/pages/Sessions.tsx:2543`.

**Why it is a problem:** Existing meetings appear deleted. This is the exact trust failure covered by P0: data appears lost even though it is only unavailable. A background refresh can also wipe a previously cached list because the non-append path does not retain prior server sessions.

**Fix:** Track a first-class server load error and last successful server payload. On failure, retain cached/current server sessions, mark them as potentially stale, show “Couldn’t refresh sessions” with Retry, and reserve the empty state for a successful empty response.

**Effort:** Medium.

### [P1] Upload status — `frontend/src/contexts/UploadsContext.tsx:170` (global Upload tray)

**User moment:** An uploaded recording is transcribing while the backend job stalls or status delivery degrades.

**What the user experiences:** REST polling stops after roughly ten minutes at line 175 without changing the upload to `failed`, `timed_out`, or another terminal/actionable state. The tray continues to treat the item as in flight and keeps showing a spinner.

**Why it is a problem:** The recent WebSocket fallback fix still has a spinner-forever terminal hole. The user has no indication whether the meeting is slow, wedged, safe to retry, or needs support.

**Fix:** When the ceiling is reached, perform one final status fetch and then set a visible non-terminal warning state such as “Still processing — check session / retry status.” Keep a manual “Check again” action and include elapsed time.

**Effort:** Small.

### [P1] Upload status — `frontend/src/contexts/UploadsContext.tsx:193` (global Upload tray)

**User moment:** The upload status socket opens successfully but the connection stops delivering frames without closing.

**What the user experiences:** `socket.onopen` immediately stops REST polling at line 197. There is no heartbeat or last-message watchdog, so an open-but-silent socket can leave the item on “Queued,” “Transcribing,” or another intermediate stage forever.

**Why it is a problem:** A WebSocket opening is not proof that progress is healthy. This recreates the same user-visible hang through a different failure mode.

**Fix:** Keep low-frequency REST reconciliation active, or restart polling when no status frame arrives for a bounded interval. Track `lastStatusAt` and surface “Status connection delayed” before declaring a failure.

**Effort:** Small–medium.

### [P1] Session processing — `frontend/src/pages/SessionDetails.tsx:611` (Session Details)

**User moment:** A user opens a newly uploaded session while its transcript and summary are still processing.

**What the user experiences:** The page fetches once. Automatic polling at lines 621–636 only runs for `metadata.reprocess_status` equal to `queued` or `in_progress`; it does not run for the ordinary `session.status === 'processing'` state. The Summary and Transcript tabs can therefore remain on “Processing…” (`frontend/src/pages/SessionDetails.tsx:2923`) until a manual reload.

**Why it is a problem:** The most natural path—clicking a just-finished upload from the tray—can land on a stale detail page that never completes in place.

**Fix:** Poll while either generic session processing or reprocessing is active, with backoff, visibility awareness, a maximum wait warning, and a visible manual refresh control.

**Effort:** Small.

### [P1] Mobile recording completion — `frontend/src/components/MobileLiveRecording.tsx:520` (mobile PWA capture)

**User moment:** The user stops a mobile recording; audio finalization succeeds, but starting the full server reprocess fails.

**What the user experiences:** A non-OK `/finalize-audio` response or network exception is only logged at lines 525–532. The UI then advances to `done` and states “Done. Server is processing” and that transcript/summary will land in about a minute at lines 705–713.

**Why it is a problem:** The displayed status is knowingly stronger than the confirmed backend state. The user may leave and wait for output that was never queued.

**Fix:** Distinguish “audio saved” from “processing queued.” If the kick-off fails, show “Audio saved, processing was not started” with Retry and a direct link to the session’s reprocess action.

**Effort:** Small.

### [P1] Mobile onboarding — `frontend/src/components/MobileSessionsList.tsx:323` (Sessions empty state)

**User moment:** A new mobile user has no sessions and taps “Record on this phone.”

**What the user experiences:** The CTA navigates to `/recording`, but the router defines `/record` and `/record/personal` (`frontend/src/AppRouterSimplified.tsx:552`). The user lands on no matching route instead of the recorder.

**Why it is a problem:** This is the primary first-run action in the mobile empty state and is a direct dead-end.

**Fix:** Route to `/record` or `/record/personal`, and add a route-level test for every CTA destination.

**Effort:** Trivial.

### [P1] Sessions search — `frontend/src/pages/Sessions.tsx:938` (Sessions search)

**User moment:** A user searches for a known meeting while keyword and semantic search endpoints are unavailable.

**What the user experiences:** Both requests can fail, producing an empty merged array. The only error handling is `console.error` at line 1015; the UI presents zero matches rather than “Search unavailable.”

**Why it is a problem:** Users cannot distinguish “no meeting matched” from “search failed,” and may conclude that content is missing or indexing is broken.

**Fix:** Track keyword and semantic errors separately. If both fail, preserve the current list and show an inline retryable search error. If one succeeds, label results as partial.

**Effort:** Small.

### [P1] Cross-meeting AI chat streaming — `frontend/src/pages/RAGChat.tsx:268` (AI Chat)

**User moment:** The user asks a cross-meeting question over a streaming HTTP response.

**What the user experiences:** Each network chunk is independently split on newline. A JSON event divided across chunks is parsed as two malformed lines and silently discarded at line 305. The component can finish with missing tokens, citations, confirmation metadata, or an empty assistant message.

**Why it is a problem:** Stream chunk boundaries are arbitrary and do not align with SSE records. Intermittently truncated answers are especially damaging in a knowledge product because they look authoritative.

**Fix:** Use a persistent SSE buffer or an event-source parser, flush the decoder at EOF, require a terminal event, and show a retryable “response interrupted” state when the stream ends without one.

**Effort:** Medium.

### [P1] TTS/podcast generation — `frontend/src/pages/SessionDetails.tsx:507` (Session Details > More)

**User moment:** A user generates spoken summary or podcast audio.

**What the user experiences:** Completion depends solely on a WebSocket. There is no authentication/org context in the constructed URL, no REST fallback, and no timeout. If the socket stays open without a terminal event, the generation control remains loading indefinitely.

**Why it is a problem:** This repeats the upload-status class of defect in another long-running job surface.

**Fix:** Centralize long-running job tracking on the existing polling abstraction, pass auth/org context consistently, add a watchdog and cancellation, and make timeout/interruption a visible retryable state.

**Effort:** Medium.

### [P1] Settings save feedback — `frontend/src/pages/SettingsEnhanced.tsx:358` (Settings)

**User moment:** A user changes recording defaults or appliance settings while the backend save fails.

**What the user experiences:** Any non-OK response or exception becomes “Settings saved locally (backend integration pending)” (`frontend/src/components/settings/SettingsLayout.tsx:233`). The actual status/reason is discarded and there is no retry action.

**Why it is a problem:** “Integration pending” sounds like a planned product limitation, not a failed save. Some values may affect only local UI while server recording continues with old defaults.

**Fix:** Separate client-only settings from server-backed settings. For server-backed fields, show “Saved on this device; server update failed,” include the parsed reason, retain a dirty/sync-needed marker, and offer Retry.

**Effort:** Medium.

### [P1] Modal accessibility — `frontend/src/components/SessionPermissionsModal.tsx:184` (Session Details > Share)

**User moment:** A keyboard or screen-reader user opens meeting permissions.

**What the user experiences:** The overlay is a plain `div` without dialog semantics, focus trapping, initial focus, focus return, Escape handling, or an accessible name on the icon-only close button. The same pattern appears in `frontend/src/components/EmailAttendeesModal.tsx:218`, `frontend/src/components/UploadTriageModal.tsx:36`, `frontend/src/pages/SessionDetails.tsx:4234`, and `frontend/src/pages/SettingsEnhanced.tsx:168`.

**Why it is a problem:** Keyboard focus can move behind the modal, screen readers are not told a modal opened, and closing can strand focus. These are core share, email, upload, reprocess, and privacy controls.

**Fix:** Migrate all overlays to `components/ui/Dialog.tsx`, require `Dialog.Title` and `Dialog.Description`, set safe initial focus, and provide labelled close controls. Add an automated dialog accessibility test.

**Effort:** Medium.

### [P1] Mobile navigation accessibility — `frontend/src/AppRouterSimplified.tsx:89` (authenticated shell)

**User moment:** A keyboard or switch-control user opens the mobile navigation drawer.

**What the user experiences:** The drawer is translated on-screen, but it is not a modal dialog and has no focus trap, Escape handling, initial focus, or focus return. The clickable backdrop is a non-semantic `div`. Background page controls remain reachable.

**Why it is a problem:** Navigation order becomes ambiguous and users can interact with hidden/background content.

**Fix:** Implement the mobile drawer with a focus-managed dialog/sheet primitive. Mark background content inert while open, focus the first navigation item, support Escape, and return focus to the hamburger.

**Effort:** Medium.

### [P1] Settings keyboard navigation — `frontend/src/components/settings/SettingsLayout.tsx:128` (Settings)

**User moment:** A keyboard user tries to move between settings categories.

**What the user experiences:** The controls declare `role="tab"` and only the active tab has `tabIndex=0`, but there is no Arrow Up/Down, Home, or End key handler. After focus enters the tab list, the remaining categories are not reachable by Tab and cannot be selected with standard tab keyboard behavior.

**Why it is a problem:** Adding ARIA roles without implementing the associated interaction model makes the control less operable than ordinary buttons.

**Fix:** Implement roving focus and arrow-key navigation per the ARIA tabs pattern, or remove tab semantics and use normal buttons/links that remain in the tab order.

**Effort:** Small.

### [P1] Admin agent truthfulness — `frontend/src/pages/admin/AgentDashboard.tsx:104` (Admin > Agents)

**User moment:** An admin opens Agent Management while the API is unreachable.

**What the user experiences:** A network exception silently replaces the real configuration with hard-coded “default agents” at lines 132–191. They are rendered as active/core/default agents with plausible model and performance data, without an offline/demo label.

**Why it is a problem:** Administrators can mistake fabricated fallback data for production configuration and make decisions or edits against a false view.

**Fix:** Never synthesize operational state. Retain the last known payload if available; otherwise show a blocking load error with Retry. If demo data is needed for development, gate and label it explicitly.

**Effort:** Small.

### [P2] Admin bulk-import status — `frontend/src/pages/AdminBulkImport.tsx:125` (Admin > Bulk Import)

**User moment:** An admin watches a queued or processing bulk import.

**What the user experiences:** Jobs and detail are fetched only on mount/filter/selection and after explicit actions. There is no polling or live update, so counts and statuses remain stale until the admin presses Refresh or navigates away and back.

**Why it is a problem:** The screen presents itself as an operations monitor but does not update during the operation.

**Fix:** Poll while any visible job is queued/processing, slow down when all are terminal, pause when the tab is hidden, and show “Updated N seconds ago.”

**Effort:** Small.

### [P2] Upload tray mobile controls — `frontend/src/components/UploadTray.tsx:59` (global Upload tray)

**User moment:** A mobile user retries, cancels, or dismisses an upload.

**What the user experiences:** Icon buttons use `p-1` around a 16 px icon, producing targets far below the 44 px mobile recommendation. They rely on `title` rather than explicit `aria-label`.

**Why it is a problem:** These are high-consequence controls next to each other; small targets increase accidental cancellation/dismissal and are difficult for motor-impaired users.

**Fix:** Use at least 44×44 px hit areas, add `aria-label`, preserve visual compactness with invisible padding, and separate destructive actions spatially.

**Effort:** Small.

### [P2] Mobile Session Details touch and iOS input behavior — `frontend/src/components/MobileSessionDetails.tsx:291` (mobile Session Details)

**User moment:** A user reviews and edits a meeting on iPhone.

**What the user experiences:** Primary header controls are 36 px, edit actions are 32 px, tab chips use `py-1.5`, and many form inputs use `text-sm` (for example transcript search at line 917 and participant fields around line 1337). On iOS, sub-16 px inputs can trigger viewport zoom.

**Why it is a problem:** The dense surface is harder to tap accurately, and repeated input zoom disrupts transcript editing and participant management.

**Fix:** Standardize mobile interactive controls at a minimum 44 px hit area and set editable mobile inputs to at least 16 px text, even if surrounding labels remain smaller.

**Effort:** Medium.

### [P2] Theme consistency — `frontend/src/contexts/ThemeContext.tsx:47` (app-wide)

**User moment:** A user selects Light or System theme.

**What the user experiences:** ThemeContext only toggles `dark`/`light` classes on `<html>`. The authenticated shell is hard-coded dark (`frontend/src/AppRouterSimplified.tsx:88`), Settings is hard-coded dark (`frontend/src/pages/SettingsEnhanced.tsx:483`), while desktop Session Details is hard-coded light (`frontend/src/pages/SessionDetails.tsx:1895`). Toasts are always dark (`frontend/src/App.tsx:75`).

**Why it is a problem:** The preference does not produce a coherent theme and moving between screens causes abrupt visual changes. Contrast has to be maintained twice through one-off colors rather than tokens.

**Fix:** Define semantic color tokens for app background, surface, border, text, muted text, success/warning/error, and apply them across the shell and pages. Drive toast theme from `effectiveTheme`.

**Effort:** Large.

### [P2] Initial bundle/perceived performance — production build output (Landing → first authenticated screen)

**User moment:** A new user signs in on a normal laptop or mobile connection, then prepares the first on-device AI recording.

**What the user experiences:** Before model weights are considered, the build emits approximately 10 MB of minified entry JavaScript across two main chunks, an approximately 895 KB transformers chunk, and a 21.6 MB WASM asset. The build warns that `BrigadeGraphViewer` is both static and dynamic, defeating part of the intended Session Details lazy-load.

**Why it is a problem:** Startup parsing/compilation competes with a roughly 880–890 MB STT model and a large LLM download. The onboarding progress UI is good, but the application shell itself is unnecessarily expensive.

**Fix:** Route-level lazy-load pages, isolate admin/rooms/graph/TTS/on-device runtimes, remove the static graph-viewer import from the default route graph, and measure cold-load LCP/INP on mid-tier hardware. Do not initialize inference libraries until the user enters recording/settings paths that need them.

**Effort:** Large.

### [P2] Knowledge Graph picker accessibility — `frontend/src/pages/KnowledgeGraph.tsx:176` (Knowledge Graph)

**User moment:** A keyboard or screen-reader user searches for a person.

**What the user experiences:** The input and absolute result list visually behave like a combobox, but expose no `role="combobox"`, `aria-expanded`, `aria-controls`, active descendant, Escape behavior, or Arrow-key result navigation.

**Why it is a problem:** Mouse users can choose people; keyboard users must tab through an unstable list and screen-reader users receive little state context.

**Fix:** Use an accessible combobox primitive or implement the ARIA combobox/listbox pattern with highlighted-option state and keyboard controls.

**Effort:** Medium.

### [P2] Mobile/desktop Sessions capability mismatch — `frontend/src/pages/Sessions.tsx:1957` (Sessions)

**User moment:** A Pro user opens Sessions on mobile intending to upload an existing recording.

**What the user experiences:** The desktop header exposes Upload Audio/Video, but `MobileSessionsList` receives no upload action and its empty state only offers recording. Global drag/drop is not a discoverable mobile affordance.

**Why it is a problem:** Upload is a core flow and common on mobile, where recordings often originate in Voice Memos or Files.

**Fix:** Add a mobile Upload action using the same file picker and triage flow, with Files/Voice Memos guidance and visible tier messaging when unavailable.

**Effort:** Small–medium.

### [P2] Recording model-load progress location — `frontend/src/components/AlwaysOnControl.tsx:1287` (desktop Record)

**User moment:** A first-time free-tier user presses Start while the browser STT/LLM assets are loading.

**What the user experiences:** Model progress is rendered at the bottom of a long recording card, below audio source, live panels, and metrics. The Start button remains visually primary while readiness/progress is distant from the action that triggered the wait.

**Why it is a problem:** Large model waits need immediate, proximate feedback. On a shorter viewport the progress indicator can be below the fold, making the action feel stuck.

**Fix:** Surface readiness next to the Start control before capture begins: model name, download size, percentage, current phase, “record now with fallback” where valid, and a persistent Settings link.

**Effort:** Small.

### [P2] Session Details diagnostic copy — `frontend/src/pages/SessionDetails.tsx:1731` (Session Details loading)

**User moment:** Any user opens a session on a slow connection.

**What the user experiences:** The loading screen shows the raw session ID and instructs the user to “Check browser console for debug logs.”

**Why it is a problem:** This is internal troubleshooting language, not actionable consumer UX, and it makes a normal slow load feel broken.

**Fix:** Show a skeleton matching the detail layout. After a timeout, offer Retry and “Back to Sessions”; keep debug identifiers behind a copyable support-details disclosure.

**Effort:** Small.

### [P2] Admin and desktop responsive layout — `frontend/src/pages/AdminBulkImport.tsx:248` (Admin > Bulk Import)

**User moment:** An admin uses the app on a narrow laptop, tablet, or mobile browser.

**What the user experiences:** Fixed four-column grids, full-width data tables, horizontal filter rows, and header action clusters have no responsive overflow/collapse strategy. Similar fixed desktop layouts exist in Agent Management.

**Why it is a problem:** Admin is part of the requested core audit scope, and operational actions can become clipped or force page-level horizontal scrolling.

**Fix:** Add table scroll containers, stacked detail metrics below `sm`, wrapping/scrollable filters, and a compact action menu for narrow widths.

**Effort:** Medium.

### [P3] Landing footer duplication — `frontend/src/pages/Landing.tsx:283` (public Landing)

**User moment:** A visitor reaches the bottom of the landing page.

**What the user experiences:** A custom footer is immediately followed by `LegalFooter`, producing two footer landmarks and duplicate Contact Support links.

**Why it is a problem:** It adds visual weight, duplicates navigation, and creates redundant landmarks for assistive technology.

**Fix:** Merge company/enterprise copy into the shared legal footer via slots/props and render one `footer`.

**Effort:** Small.

### [P3] Landing test/product-copy drift — `frontend/src/__tests__/Landing.test.tsx:31` (CI / Landing)

**User moment:** Indirectly, this affects release confidence for the signup funnel.

**What the user experiences:** No immediate runtime failure, but the test suite is red because the expected H1 no longer matches `frontend/src/pages/Landing.tsx:104`.

**Why it is a problem:** A permanently red test stops distinguishing regressions from intentional copy changes and weakens confidence in the highest-value unauthenticated flow.

**Fix:** Decide the canonical positioning, update the test and page together, and prefer assertions around stable funnel semantics rather than full marketing sentences unless exact copy is contractual.

**Effort:** Trivial.

## Quick wins

1. Fix the mobile empty-state route from `/recording` to `/record`.
2. Preserve Sessions data and show an inline retryable error when server fetch fails.
3. Mark upload tracking as delayed/actionable when its polling ceiling is reached.
4. Add a last-message watchdog to upload status WebSockets.
5. Poll generic `session.status === 'processing'` in Session Details.
6. Do not show “Server is processing” when `/finalize-audio` failed; add Retry.
7. Replace the Session Details loading debug copy with a skeleton and delayed Retry.
8. Increase Upload tray and mobile Session Details hit areas to 44 px.
9. Add a mobile Upload action.
10. Update the Landing test and remove the duplicate footer.
11. Stop fabricating admin agent data on API failure.
12. Add polling and “last updated” to Admin Bulk Import.

## Bigger bets

1. **One long-running-job state machine.** Use a shared abstraction for uploads, reprocess, imports, TTS, digests, and model downloads: authenticated start, live updates, REST reconciliation, heartbeat watchdog, terminal timeout, retry, cancellation, and visible elapsed time.
2. **One modal/sheet system.** Move every overlay to the Radix wrapper and add a responsive sheet variant for mobile navigation and action menus.
3. **Semantic design tokens and real theming.** Replace page-local `gray`/`zinc`/white choices with surface/text/border/status tokens that support both light and dark modes.
4. **Route-level code splitting.** Split public marketing, authenticated core, admin, rooms, graph, TTS, and in-browser inference into independent route chunks. Keep ONNX/transformers/WebGPU code out of the default shell.
5. **State-aware first-run journey.** Make Landing → signup/login → device capability → model readiness → mic test → first 60-second recording a single measurable funnel, with a capture-only branch for mobile and an explicit unsupported-browser branch for free-tier local mode.
6. **Responsive Session Details redesign.** Converge desktop and mobile on shared content components and state semantics rather than maintaining a light desktop implementation and separate dark mobile implementation.
